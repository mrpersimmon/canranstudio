## 共同入口与基本流程

建议页面命名“我的纪念卡”，课程首页保留“我的课程 / 我的纪念卡”两个直接入口。页面属于当前登录学生，不再输入姓名或重新注册。

建议流程：登录 → 我的纪念卡 → 点选卡片 → 放大查看 → 保存纪念卡。返回时恢复原来的浏览位置。课程结算页也可进入收藏页，进入收藏页不需要重新加载或完成该课程。

第一版聚焦查看和保存。页内主要信息只有卡片、姓名、星数、课号与有效的首次五星日期。卡片本身是可键盘操作的按钮，外观明确；缩略图下的“查看纪念卡”与点击卡片执行同一动作。

## 三种页面方案

### A：卡片陈列（推荐）

桌面两列呈现，手机一列。三种课程配色共同构成陈列层次；卡片之外留白，点一张便可放大。数量增加后继续纵向浏览。默认按 Lesson 课号排列；不会因反复查看或多亮一颗星而突然换位置。

优点是查找直接、移动端容易适配，开发和维护工作量最低。它把已确认的卡面放在主体位置。取舍是翻阅仪式感弱于纪念册。

![A：卡片陈列](visuals/2026-10-09-0026-v0.15/collection-gallery.png)

首张生成草稿出现了多余口号且缺少 Lesson 5–6 课号，已通过第二次 imagegen 修正；本处只采用修正后的文件。

### B：翻页纪念册

一次突出一张卡，下方用缩略图选择课程，左右按钮切换，卡片下方保存。手机保留明确切换按钮，滑动只作为补充，不要求孩子猜手势。旧版本可在当前卡详情内展开。

优点是单张作品完整且有纪念感。取舍是卡片多时查找较慢，切换状态、焦点和手机高度处理更多。手机需把卡片控制在约 340px 宽，长姓名另行适配。

![B：翻页纪念册](visuals/2026-10-09-0026-v0.15/collection-album.png)

### C：成长时间线

未满星卡置于“正在点亮”区；满星卡按真实首次满星日期倒序排列，日期相同按课号排列。日期明确标为“首次满星”，不把它混作首次打开、收录或下载日期。

优点是学习经历的顺序清楚。取舍是每张卡占用纵向空间较多，按具体课号找卡不如陈列。手机把日期放到卡片上方，不保留拥挤的左右三列结构。

![C：成长时间线](visuals/2026-10-09-0026-v0.15/collection-timeline.png)

三张图使用同一组虚构数据：小雨，Lesson 1–2 五星（2026.10.07）、Lesson 3–4 五星（2026.10.08）、Lesson 5–6 三星且无日期。图上数据与按钮只用于比较布局，不是学生实际成绩或已实现功能。

## 建议的收藏规则（本轮提案）

| 情况 | 建议行为 |
| --- | --- |
| 零星 | 不占收藏位；没有卡片时显示“还没有纪念卡”及“去上课”按钮 |
| 第一颗星获服务器确认 | 自动收录，不另设“领取”门槛 |
| 同版一至四星 | 在同一张卡上更新星星，使用棕边，不显示首次满星日期 |
| 同版第五颗星 | 原卡升级金边，读取服务器首次满星日期 |
| 重开练习、反复查看或保存 | 不撤销已获星、不新增重复卡、不改首次五星日期 |
| 离线作答 | 保留待同步成果；同步确认前不冒充账号已颁发成果 |
| 正式收藏版本更新 | 旧版及其素材保留；新版本独立记录，不以换图自动补发新版本星星 |
| 普通图片修补 | 不自动产生一张新的可收藏卡；补丁与正式收藏版本分开管理 |
| 换班或课程暂停开放 | 建议保留已获卡片的查看与下载；是否可继续挑战仍由课程权限控制 |
| 账号退出或切换 | 立即移除上一位学生的可见内容和私有缓存；新身份验证后显示其本人收藏 |

建议收藏主列表每课显示当前已拥有的最新正式版本，旧版本放在该课详情的“往期纪念卡”入口；版本很多时也不会挤满首页。已获得的旧版始终可找回；未获得的新版不顶替已有旧卡。已有旧证书不自动转换成新版五星：有可核验资料的，按原版规则归档；仅存在本机的历史资料不能冒充账号成果。

姓名始终来自账号资料，不提供自由填写。按现行规则，改名后展示与新下载使用当前账号姓名；获星事件及首次满星日期保持不变。以前下载到个人设备的图片自然保留当时的姓名。

## 实现方式

三种布局共用同一套账号收藏能力，选界面时不必再选一套存储系统。

### 已有基础与缺口

本地现有 [server/store.js](../../server/store.js) 已有 `unit_awards` 表，主键为学生、课程、奖励版本，且首次满星时间由服务器记录。获星与可重开练习分开保存。

[server/app.js](../../server/app.js) 当前主要在进入单课和提交进度时返回该课当前版本奖励，没有学生全部证书的集合读取入口。[core/story-certificate.js](../../core/story-certificate.js) 的场景、课号和导出名称仍绑定 Lesson 1–2，实施前需配置化。不能仅给旧证书页添加一个列表链接便宣称三课收藏完成。

### 推荐结构

1. **现有服务器数据库保存成果。** 继续使用账号系统的 SQLite，按学生、课程、奖励版本读取已获星与首次日期。数据库保存成绩记录及模板标识；数据库与历史素材一起纳入已有备份流程。
2. **卡面按版本保存。** 建立受版本控制的纪念卡模板目录，描述称号、课号、主题色、人物图、字体、渲染版本。保存旧模板和旧素材，避免更换图片导致老卡悄然变样。
3. **一个共用渲染器。** 收藏缩略图、放大查看和高清 PNG 共用同一份奖励快照及模板。沿用登录姓名与 1640×880 导出尺寸；查看或下载都不触发颁奖。下载前等待字体、人物图和星星准备完毕。
4. **增加本人收藏接口。** 建议 `GET api/me/certificates`，身份取自登录会话，不接收前端指定的学生身份；返回该学生所有已拥有版本的摘要与合法卡面资源。按需读取某张卡的详情。路径通过当前部署前缀生成，兼容根目录部署与本地带前缀预览。
5. **收藏权限与开课权限分别核验。** 已获卡片可以查看，不因此授权进入暂停开放的课。卡面资源只提供渲染需要的素材，不下发整课题目包。任何学生都不能通过修改地址读取另一位学生的成绩或姓名。
6. **加载与缓存。** 公共且不含身份信息的版本化画面素材可以缓存；个人收藏记录由服务器核验并按账号隔离。进入收藏页先准备首屏卡面，后续按行预加载；每张卡的图、星星、字体准备好后再完整展示，避免半张画面。点开放大卡时也执行完整性检查。下次进入复用已缓存素材并刷新本人记录；网络异常时明确说明正在展示上次同步记录，不能把未同步成果当成已颁发记录。首访离线不能承诺可加载尚未缓存的卡面。

日常展示由浏览器基于记录和模板生成，保存时输出 PNG，无需为每颗星的每次变化在数据库里保存一张完整图片。如果将来需要正式盖章 PDF 或固定签发件，再增加服务器生成与归档，当前收藏需求不必引入它。

## 推荐实施顺序与验收

1. 将 Lesson 3–4、5–6 的已确认插图拆成可复用素材；把纪念卡组件配置化。按教材目标核查两课恰好五个答题区，保留必要题目与综合覆盖，接入现有严格获星规则。
2. 增加本人跨课程、跨版本的收藏读取与历史模板查询。对现有奖励表做保留数据的增量迁移，不清空学生、班级或学习记录。
3. 实施选定的收藏列表、卡片详情、保存与返回，并增加首页、结算页入口。先完整接入已确认的这三组，其他课程继续独立迁移。
4. 通过真实页面验收下面行为，再按用户要求分别提交、推送、发布。

验收必须覆盖：不同学生及切换账号隔离、换设备恢复、首星自动收录、零星空状态、三颗星无金边无日期、第五颗星金边及日期固定、旧版与新版本并存、重复上报不重复收藏、练习重开不删奖励、无课程权限时仍能看已获卡但无法进入课程、离线待同步与恢复、素材失败重试、长姓名、320/390/768/1280 宽度、键盘焦点、高清下载内容一致，以及真实安卓微信的图片保存体验。
