# 页面可读性防护网

2026-09-06。适用 `codex/duolingo-version` 的 Lesson 1–6，当前深色地图与浅色课内体验。

## 这次为什么漏检

用户截图中，课文第一句的颜色为 `#f1f7f8`，气泡为 `#eef1e8`，对比度只有 1.055:1。页面加载时直接给 `body` 写入深色背景和白字；课内样式只给 `:root` 设置浅色主题，不能覆盖子元素 `body` 已经声明的颜色。透明课内容器继承白字，使用 `multiply` 的人物图片与深色页面相乘，导致同时变黑。页面资源全部加载成功，仍然无法阅读。

先前 55 项程序检查主要覆盖课程、音频事件、记录和资源包。截图验收聚焦新地图，未在相同版本中截图检查进入课程后的界面。程序通过和地图通过被错误扩大为整套体验通过。历史报告已明确更正，不能作为本次通过证据。

## 修复约束

- 加载页的背景和文字只作用于 `.course-package-shell`。
- 课内 `body`、`.lp-shell`、`.lp-blocked` 成对声明浅色背景与深色文字；容器隔离图片混合。深色地图拥有自己的成对覆盖。
- 对话气泡与保存提示明确声明文字色，避免从地图继承。
- 异常恢复使用与普通页面一致的 `render` 流程，退出地图主题。
- 地图说明文字及课内蓝色小字满足对比度门槛。
- 地图猫猫和关卡共用有预留高度的一行，站在节点另一侧；展开关卡说明时收起装饰猫，避免覆盖按钮。这个问题是在完成若干关后的窄屏回归中发现的。
- 词句题场景的网格行采用明确高度约束，图片不能因自身尺寸撑开网格并压住角色名。
- 课程内容、音频、课程进度版本和存储格式不变。

## 自动检查覆盖

浏览器使用真实 HTML 中的加载样式、正式 CSS、场景渲染器、控制器与运行时。测试适配器只替换课程包下载、存储、时间和音频完成事件：所有题目和答案仍取自正式 catalog，所有推进通过正式控制器按钮执行。

| 范围 | 规则 |
| --- | --- |
| 四种屏幕 | 320×568、420×856、906×801、1440×900 |
| 课程内容 | catalog 中每一个活动 ID，在每种屏幕都必须有渲染检查；当前为 52 个活动、11 个节点 |
| 页面切换 | 加载、地图、故事前两句、课本六课、各关完成、复习、复习完成、返回地图、重新进入 |
| 控件状态 | 未选择、选择、错误、提示、正确、单词听完、配对完成、关卡介绍 |
| 异常路径 | 保存失败提示、重试、控制器异常页面、恢复地图 |
| 文字 | axe-core 检测实际前景色、背景色；普通文字至少 4.5:1，大文字至少 3:1 |
| 图片 | 加载成功、教学图片可见、没有压暗滤镜/透明度、multiply 不落在深色背景上 |
| 操作 | 主要按钮至少 44×44；实际命中测试检查是否被其他元素盖住；没有横向溢出 |
| 负向对照 | 主动制造浅底白字、深底混合、缺失图片，必须逐一被检出 |

滚动历史中被裁切的文字，会滚动到可见位置再次做同一对比度检查；窄屏长题中处于固定底栏后的选项，会实际滚动并重新做命中检查。它们不会被直接排除。检测库无法判断的装饰箭头，只在证明其不覆盖文字且按钮背景完全不透明时，计算精确对比度并记录几何数据；保存弹窗的文字额外进行多点命中核对，再核算不透明表面上的对比度。其他未决项仍失败。

标准依据：[W3C 对比度规则](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。检查实现参考 [axe-core 官方 API](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)；持续集成参考 [Playwright 官方 CI 说明](https://playwright.dev/docs/ci-intro)。

## 如何执行和拦截

在 Codex 内置浏览器中：先运行 `npm run build:course`，再运行 `npm run visual:serve`，打开输出的 `/__qa__/runner.html`。页面自动执行整套检查并将结果写到 `test-results/`。测试服务器仅监听本机回环地址，测试页面和适配器不会进入发布包。

需要复核本次三个布局/异常场景时，打开 `/__qa__/runner.html?inspect=regressions`。检查会在对应视口暂停，完成目视检查后点击“继续检查”；全部状态仍须通过才能生成证明。

CI 运行 `npm run test:browser`，用 Playwright 打开同一个页面。CI 驱动不会采用另一套较弱的检查。

`npm run verify:visual` 和 `npm run build` 要求一份有效的浏览器通过记录。缺失、失败、状态覆盖不足、负向对照未生效或指纹过期，都会返回非零状态，发布包不会生成。指纹包含实际发布输入、图片、字体、CSS、入口、课程内容、检查代码和依赖锁。不能修改代码后沿用旧记录；失败运行也会撤销已有通过记录。

`npm test` 只表示逻辑及防护网契约测试通过。它不是页面视觉通过的证明。

## 每次交付仍需看实际页面

自动检查后，从真实首页进入课程，使用原始音频及真实存储，检查目标问题在相同状态和尺寸下是否消失；至少检查历史/当前气泡、人物全身、答题选项、底部操作、返回地图与课本。修改全局颜色、根容器、图片混合、固定定位或响应式规则时必须重新执行整套矩阵。

保存同尺寸的前后截图、重点区域对照、浏览器错误记录及本次报告。根目录 `design-qa.md` 只有在这些检查完成后才能写 `final result: passed`。无法取得页面证据或仍有 P0/P1/P2 问题时写 `blocked`，并列明具体问题。

这套自动检查针对可读性、遮挡和主题泄漏；音频的模拟完成事件不构成试听结果，也不证明所有浏览器和所有视觉差异都已验收。
