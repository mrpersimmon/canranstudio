## 已确认的加载流程

1. **先准备启动包。** 入口以 4 个并发下载准备 76 项脚本、样式、字体、全书课程数据、媒体索引和部分通用图片。进度条对应这份启动包，本次记录为 3,672,830 字节，其中没有 MP3；不代表全书图片和录音已经下载。另有 2,836 段录音和 108 项图片共约 65.4 MB 被列为延迟媒体。
2. **做有限的入口预热。** 入口只指定第一句 D01 预热，最多等待 180ms；进入时解码的图片主要来自角色列表。当前第一关的手提包没有进入这份预解码集合。
3. **进入活动后，按需请求图片。** 场景创建普通 `img` 并采用异步解码。图片未加载完时，活动界面仍然可以出现；没有“本关所需图片全部就绪”的进入条件。
4. **使用时准备语音。** 实际播放每次新建 `Audio`，设置 `preload=auto` 后立即调用 `play()`。D02 和后续录音没有提前准备下一句的流程。D01 的预热对象也没有被当前播放器取走复用。
5. **完整获取、校验后才交给浏览器。** Service Worker 首次遇到未缓存媒体时，会向源站获取完整文件，检查大小和 SHA-256，保存后再返回。音频即使发起范围请求，源站侧也获取整文件，再由 Service Worker 合成 206 响应。
6. **后续复用已获取内容。** 再次播放或再次进入会受益于缓存，因此首次使用和重复使用的感受可以差很多。但命中的媒体仍需读取和校验；暖启动也仍会检查启动清单及 76 个缓存条目。离线只能使用已经取得的素材，未下载的录音仍需要网络。

这里需要区分“文件已经保存”和“图片已可显示、声音已可播放”。修正前的入口准备和播放器状态没有完整表达后一个条件。普通听音流程提前进入逻辑上的 `playing` 状态，页面可能先显示暂停操作；它没有对应浏览器 `waiting/canplay` 的明确等待状态。

## 官网浏览器实测

使用独立 Playwright Chromium 会话，420×856，自然网络，不做限速，不改变用户的浏览器资料和答题记录。以下是这次会话的实际样本，不是设备或网络环境下的性能保证，也不是统计分位数。操作之间包含调查所需的停顿，可能影响连接复用。

| 场景 | 实际时间 | 量度含义 |
| --- | ---: | --- |
| 空缓存首次打开 | 13.98 秒 | 导航开始到路线 DOM 出现 |
| 同会话刷新后打开 | 1.15 秒 | 导航开始到路线 DOM 出现 |
| 第一关手提包 | 2.79 秒 | 图片节点插入到 load 事件 |
| 第二句 D02 首次播放 | 1.16 秒 | 点击“继续”到原生 playing 事件 |
| 同句 D02 重听 | 22 毫秒 | 点击“重听”到原生 playing 事件 |
| 第三句 D03 首次播放 | 1.37 秒 | 点击“继续”到原生 playing 事件 |

首次打开时，课程数据约 2.64 MB 的请求耗时 7.66 秒，媒体索引请求耗时 2.71 秒。第三句录音约 23 KB；独立记录到 Service Worker 发起的源站请求约 1.334 秒，浏览器收到媒体响应约 1.343 秒，说明这一样本的主体耗时在联网获取。不能把它统称为文件太大、解码慢或设备性能差。

这些记录复现了“页面已经出现后补图”和“操作之后等到语音开始”的症状。图片 load 与浏览器 playing 均是技术事件；本次没有测量屏幕首次实际绘制或声卡首个非静音采样，也没有声称所有图片、语音都有相同延迟。

## 为什么之前的检查没有暴露等待体验

- 全量浏览器题目检查使用能立即播放的模拟音频，结束由测试触发，不代表真实下载和起播时间。
- 图片检查在断言前等待解码完成，检查最终完整性和布局，会跳过用户看到空位的时间。
- 真实语音验收证明了能够播放并收到 ended；没有给“点击到 playing”设置验收要求。
- 大量状态检查、文件 SHA 校验和最终截图通过，不能证明素材及时出现。这轮应将加载时序作为独立验收范围。

## 已确认的设计决定

已定：先解释现状并记录实际证据；保持已有题目、判题、进度与音效行为；本轮不实施性能改动。术语沿用 [CONTEXT.md](../../../CONTEXT.md)，区分课文主题和关卡。

**Q1 已确认：按关卡准备。** 用户答复“按你推荐的来”。进入一关之前准备本关必需的图片、语音和反馈音效；学习时再准备下一关。本轮不再询问是否选择按关卡准备，也不扩大为整个主题或全书下载。

已形成的执行细则建议：沿用准备页面，显示“正在准备本关”和实际进度；准备完成后自动进入关卡。后台准备下一关时，当前关卡的播放和操作优先；命中有效缓存就复用。刷新恢复之前的题目与进度，准备和后台下载不算学习完成，不消耗机会。继续保持最后一题先显示对错、学生点击继续后结算。

用户随后答复“都按照推荐的来”，确认以下两项：

- **Q2 已确认：按重要性处理失败。** 题目图片、教学语音等必要素材失败时留在准备页，提供“重试”和“返回路线”，已经成功准备的内容保留；装饰图和反馈音效仍提前准备，但单独失败时可以进入，保留文字与颜色反馈。
- **Q3 已确认：手机和平板优先，兼容电脑。** 图片解码、音频预热、后台准备的内存与并发安排遵循这一优先级。移动尺寸的自动化结果与真实手机、平板结果分别记录。

等待反馈的具体文案、缓存去重、调度并发和预热对象复用属于上述方案中的实现细节；不另开重复确认。完整的准备流程、异常恢复与验收要求已归入 [实施方案](implementation-plan.md)。上一轮自然网络的单次测量仍只作基线，不作为所有设备的性能保证。
